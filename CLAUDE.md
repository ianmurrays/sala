- Sala has no server: the iOS app talks to Aula directly. `ios/Sala/Aula/` holds the session (`AulaSession.swift`: tokens, cookies, CSRF, refresh) and the routes (`AulaRoutes.swift`, `AulaMapping.swift`) that answer `APIClient` in-process, in the shapes `API.md` describes.
- Login is MitID in a web view (`ios/Sala/LoginView.swift`) that catches the OAuth redirect to `app-private.aula.dk`. Never start or retry MitID on your own: repeated failed attempts can lock the identity.
- `ios/project.yml` (XcodeGen) is the source of truth for the iOS project: change it, run `xcodegen generate` in `ios/`, and commit the regenerated `Sala.xcodeproj`. CI fails when they drift.
- Signing (team, bundle ID prefix) lives in the gitignored `ios/Config/Local.xcconfig`. Simulator builds need it too: unsigned, the app has no Keychain access and silently drops its settings. To build and install on a phone: `ios/scripts/install-device.sh "<device name>"`.
- Tests: `cd ios && xcodebuild test -project Sala.xcodeproj -scheme Sala -destination 'platform=iOS Simulator,name=<an iPhone simulator>'`. The golden tests in `ios/SalaTests/` replay recorded Aula answers (from the old Python server on its fake Aula, now frozen in `ios/SalaTests/Goldens/`) and check the Swift answers and writes against the server's. A route change means editing its golden by hand.
- Demo mode: a debug build launched with `-demo YES` runs on a fake Aula (`ios/Sala/Aula/DemoAula.swift`) answering from `ios/DemoAula/<method>.json`, no login. Use it to run and check the app in the simulator; launch through the device tools' `open <bundle id> --relaunch --launch-args -demo --launch-args YES`. It never calls Aula or touches the saved Aula login.
- Keep the demo fixtures current in the same change as the code: a new Aula method (read or write) gets `ios/DemoAula/<method>.json`; a new field, param or screen gets data in the fixture that shows it; a removed method loses its file. Fixture data is invented (never from `.cache/` traffic), dates written as if today were 2026-11-13 (`DemoTransport.anchor`). Format and matching rules: the comment on `DemoTransport`. `DemoTests` enforce coverage; a new screen adds its reads to `testEveryScreenWorksOnTheFixtures`.
- Where fields sit in Aula's live responses: `docs/aula-shapes/` (captured from real Aula, anonymised).
- Working on an Aula call: the `aula-api` skill. `scripts/aula-bundle.py` searches the web portal's JS for `?method=` calls; `scripts/pull-aula-traffic.sh` pulls what a debug build captured (Settings → Debug → Capture Aula traffic). Captured traffic is real families' data: it stays in `.cache/`.
- CI (`.github/workflows/ci.yml`) runs gitleaks, the project drift check and the iOS tests.
- Keep `README.md` current: when a change adds, removes or renames a user-facing feature, or changes the build, setup or test steps, update the README in the same change.
